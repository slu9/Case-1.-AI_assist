# Campaign Assistant

AI-ассистент заведения рекламных кампаний (хакатон SibКод, кейс 1). Менеджер описывает кампанию словами, агент на GigaChat собирает её целиком: параметры, аудиторию, места показа, баннер, промо-экран и креативы. Затем проверяет результат, показывает превью и после подтверждения человека отправляет на модерацию.

## Запуск

Нужен Docker и ключ GigaChat (Authorization Key из личного кабинета).

```bash
cp .env.example .env
```

Впишите ключ в `GIGACHAT_CREDENTIALS`, затем:

```bash
docker compose up --build
```

Интерфейс откроется на http://localhost:3000. Роль менеджера или модератора переключается в профиле в нижнем меню. База хранится в томе Docker, сбросить её к мокам:

```bash
docker compose down -v
```

Если ключ от корпоративного тарифа, поменяйте `GIGACHAT_SCOPE`. Модель меняется через `CAMPAIGN_LLM_MODEL`, по умолчанию `GigaChat-3-Ultra`.

## Как это работает

```text
Браузер (Next.js) ── чат, превью, модерация
   │
   ├── сервис ассистента (backend/server.py) ── агент + GigaChat
   │        │ только HTTP, как внешний клиент
   └────────┴── API кампаний (backend/api.py) ── SQLite, моки
```

1. Каждое сообщение уходит агенту вместе с актуальными справочниками. Модель отвечает текстом или вызывает инструменты.
2. Кампания собирается в черновике внутри сессии, поэтому состояние сохраняется между сообщениями. JSON баннера и контента проверяется Pydantic до обращения к API, ошибка возвращается модели, и она исправляется сама.
3. Пишущий инструмент не выполняется, пока человек не подтвердит его в интерфейсе. Это обеспечивает код, а не промпт. Заведомо невалидное действие отклоняется до показа подтверждения.
4. `apply_draft` записывает черновик одной цепочкой: кампания, сегменты, баннеры, контент, креативы. При сбое повторный вызов продолжает с упавшего шага и не создаёт дублей.
5. Бэкенд ведёт аудит всех пишущих операций, агент ведёт свой журнал действий: кто, что и когда.

### Что проверяется кодом, а не просьбой к модели

- Подтверждение человека перед любым изменением.
- На вопрос агент получает только инструменты чтения: менять кампанию можно лишь в ответ на просьбу.
- На модерацию кампания уходит только по прямой просьбе менеджера.
- Существующая кампания открывается в черновик и обновляется, копия вместо правки не проходит.
- Правила состояния кампании приходят вместе с её данными, поэтому запреты агент объясняет по фактам.
- Дата окончания: кампанию нельзя создать, пока менеджер не назвал дату или не сказал прямо, что окончания нет.
- Числа и промокоды в текстах креатива должны быть в словах менеджера, адреса ссылок берутся только из брифа и списка известных. Выдуманные условия не проходят.
- Баннер без заголовка и креатив без привязанного промо-экрана не проходят.
- Вес кампании считается по критериям, модель не может его подменить.

### Вес кампании

Шкала от 0 до 12, как в моках. Менеджер может назвать своё значение, тогда расчёт отключается. Итоговый выбор показа делает внешняя система показов (`task.md` §10.7).

| Критерий | Баллы |
|---|---|
| Тема | События 6; продажи и ретаргет 5; лайфстайл 4; доп. услуги и рекомендации 3; советы, подсказки, финансы и курсы 2; остальное 1 |
| Срок | до 14 дней +3; до 31 дня +2; до 62 дней +1 |
| Аудитория `ALL_USERS` | +2 |
| В брифе «широкий охват», «приоритет», «срочно», «важно» | +2 |

### Изображения креативов

Картинку рисует GigaChat в два шага: сначала называет простой предмет по смыслу рекламы, затем рисует минималистичную 3D-иконку этого предмета в палитре сайта. Людей на изображениях нет (`task.md` §10.9). Первая картинка занимает около 20 секунд, дальше берётся с диска. Настоящий адрес в `image` креатива важнее генерации.

## Устройство

- `backend/domain.py`: модели домена и каталог ошибок.
- `backend/db.py`: таблицы, чтение моков и наполнение базы.
- `backend/api.py`: API по §3 `task.md` с жизненным циклом, ролями, валидацией, аудитом и заглушкой CBRO.
- `backend/llm.py`: контракт модели `LLM` и адаптер GigaChat. Другая модель подключается новым адаптером без правок логики агента.
- `backend/tools.py`: 31 инструмент по одному на вызов API, 9 инструментов черновика и сам черновик. JSON-схемы получаются из моделей Pydantic.
- `backend/agent.py`: цикл с подтверждением и журнал действий.
- `backend/server.py`: сервис ассистента для интерфейса и генерация изображений. Сессии живут в памяти и пропадают при перезапуске.
- `backend/system.md`: системный промпт, отделён от кода.
- `web`: интерфейс на Next.js.
- `docs/tools.json`: описание инструментов с JSON-схемами.
- `docs/dialogs.md`: записанные диалоги с настоящей моделью.

Реальный API подключается заменой `CAMPAIGN_API_URL`: агент ходит в бэкенд только по HTTP.

## Решения там, где спека молчит

- Создание дочерней сущности (`POST`) подчиняется тем же правилам, что и её правка: в `ON_MODERATION` и `STOPPED` запрещено, в `APPROVED` снимает одобрение.
- Удаление баннера удаляет его креативы, удаление контента отвязывает его от креативов.
- Записи аудита переживают удаление кампании.
- Советы по аудитории не входят в `GET /warnings`: их показывает ассистент.
- Строгий режим схем у инструментов не используется: в них есть произвольные объекты стилей, а проверку делает Pydantic на входе в инструмент.
- Превью рисует креатив в стиле сайта, цвета фона из JSON в нём не используются. JSON креатива при этом остаётся по схеме §2.6.

## Данные

Используются только материалы организаторов:

- `data/mocks/`: 11 JSON из 18.
- `data/mock-data.md`: отсюда читаются справочники, JSON которых нет: темы, теги, типы сегментов, сегменты, места и задокументированные переходы кампаний 102, 104 и 114.

Если оригинальный файл появится в `data/mocks/`, он заменит данные из таблиц. Чего в материалах нет, того нет и в базе: подписи 5 тем и всех типов сегментов равны их кодам, а у журнала других кампаний нет истории до запуска.

`validation_rules.json` отсутствует, поэтому заведены только 12 кодов ошибок, названных в документации. Остальные нарушения возвращаются с кодом `VALIDATION_ERROR`, а суть описывают `field` и `message`.
